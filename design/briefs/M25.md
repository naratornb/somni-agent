# M25 Execution Brief — Grooming Sessions

PRD: issue #38. Slices: #39 (items-from-birth), #40 (honest busy), #41 (lifecycle + Sessions page), #42 (Home rail), #43 (work units), slice 6 (interrupted/resume + native notifications — issue TBD, blocked on research note re `--resume`).

Source of record: the 2026-09-03 grilling decisions, restated in the PRD. This brief adds only what implementers need beyond it.

## Non-negotiables (repo rules that bite here)

- Two vocabularies never mix: session states (`working / queued / needs-review / interrupted / done / archived`) are grooming machinery — they never appear in `ItemStatus`, and Item `Status` never gains members.
- All logic in main; renderer renders stored state + IPC events only. Invoke for commands, push for transitions.
- `.somni/` files are truth. Session state lives in item frontmatter (flat `key: value`, see store.ts) — write transitions atomically *before* acting. In-memory queue = derived.
- No new dependencies. The session manager is one small boring module mirroring the drain-loop idiom (`executor.ts` `drainLoop`/`sleepOrWake`/`wakeDrain`), not a job-queue lib.
- Runner differences stay behind the Runner adapter. Resume = `resumeSessionId` through `turn()`; last sessionId line in the transcript wins (existing chat.ts convention).
- Ready gate untouched. Apply (`applyProposal`) remains the only mutation out of any chat.

## The seam (agreed with the user)

All behavioral tests drive public main-module APIs with a fake runner adapter plugged in at the Turn seam — `executor.test.ts` / `chat.test.ts` / `turn.test.ts` are the prior art. Assert on frontmatter, transcripts, emitted events, queue order, argv. The notifier + focus-check are injected dependencies of the session manager so Vitest never touches Electron (`Notification`, focus). New views get SSR smokes in the views suite.

## Slice-specific notes

- **#39**: killing `DRAFT_KEY` touches chat.ts, App.tsx (`groomSeed`/`autoRun` handoff), GroomView load effect, Capture "Groom now", BoardView entries, and `applyProposal`'s `_draft` rename branch (dies — the item already exists; Apply converts in place). Auto-title: cheap one-shot read-only Turn after the first exchange (report.ts compact-summary precedent), item rename via existing `saveItem` move. An abandoned empty groom = an idea item with an empty spec — acceptable Backlog noise, deletable; do not build cleanup.
  - *Decisions taken during implementation:* the placeholder name is `NEW_GROOM_NAME = 'New groom'` (chat.ts) and is the auto-title's only trigger — the title Turn fires once, after the first exchange, and re-reads the item before writing so a manual rename mid-turn wins. Turn-1 context is suppressed while the item is still the placeholder with an empty spec (nothing worth seeding). New main API: `startGroom(repo)` → `groom:start` IPC, plus `store.updateItem`/`store.renameItem` (`setItemStatus` now delegates to `updateItem`) and an `item:rename` IPC for the header affordance. `ChatEvent` gains a `title` variant so the Groom header updates without a repo reload. Grooms are created with status `grooming`, so they join `backlog.json` ordering only at Apply (now for every Apply landing in Backlog, not just the ex-scratch path).
- **#40**: buffer streamed text per key in main (chat.ts already owns the closure) and replay it on `chat:load`; `busy` is already returned — consume it. Toast = renderer concern fed by the existing `chat:event` channel going global (App-level listener, not per-view).
  - *Decisions taken during implementation:* `loadChat` gained a third field, `partial` (a module-level `partials` map filled in `onText`, cleared alongside `inFlight`); GroomView applies it as the streaming buffer only when `busy`, which also re-disables the composer/Send/Propose Now/mic (they already keyed off `streaming !== null` — no new busy flag). The in-flight bubble moved into `chatShared.StreamingBubble`, which renders "Thinking…" before the first token and the cursor after, and is SSR-smokeable in isolation (effects never run under `renderToStaticMarkup`, so the busy state is untestable through GroomView itself). App keeps its own `chat:event` listener purely for the toast — it ignores everything but `done` and suppresses the toast when that slug is the open Groom, so it never duplicates GroomView's rendering. Toast is fixed bottom-right, auto-dismisses after 8s, and offers Open (switches to that Groom, name resolved from loaded items) plus Dismiss.
- **#41**: statuses in frontmatter; auto-archive sweep on `repo:load` (ensureSomni precedent — no timers). Sessions list IPC derives from `loadRepo` items, no new index file.
  - *Decisions taken during implementation:* the frontmatter field is `groomState:` (union `working | queued | needs-review | interrupted | done | archived`, absent = plain active conversation) plus `doneAt:` — the whole union is declared now, so #43/#44 add transitions only, never a migration. The Sessions page filters by kind *and* by session state (the `state` option of `sessionGroups`, which narrows to that one group). No sessions IPC at all: `Item` already carries the fields, so the page is a pure projection of the `repo:load` payload (`sessionGroups` in ui.ts, unit-tested); the only new IPC is `session:reopen`. Transitions: `applyProposal` → `done` + `doneAt`; a finished turn whose reply parses as a Proposal → `needs-review`; any `chat:send` clears `groomState`/`doneAt` back to active (covers reopen-by-typing, re-groom of an applied item, and dismiss-then-continue — there is no dismiss IPC, dismiss is renderer-only). `archiveStaleSessions(repo, now)` (store.ts, `ARCHIVE_AFTER_DAYS = 14`, idempotent) runs inside the `repo:load` handler. Page groups: a fifth group **In conversation** was added for sessions with no state — without it the page is empty for most users; `interrupted` shares the "Needs your review" group. Nav glyph reuses `chat_bubble` (Groom is not a nav destination), so the icon subset is untouched. Session chips are their own `SESSION_CHIP` map in the `STATUS_CHIP` formula — a session state never borrows an Item Status label.
- **#42**: pure composition in HomeView + a small ordering helper; reuse `STATUS_CHIP`/`CHIP_SM` atoms.
  - *Decisions taken during implementation:* one new pure helper, `railOrder(items, cap = RAIL_COMPACT_CAP /* 6 */)` in ui.ts → `{ focused, compact, overflow }` — it reuses `isSession`/`sessionActivity`, excludes `archived`, takes the freshest session as `focused` and stable-sorts the remainder by `needs-review | interrupted → working → queued → rest`, so activity order breaks ties without a second sort key. HomeView gained optional `items`/`onGroom`/`onViewAll` props (optional so the existing SSR smokes and the no-session repo render exactly as before — the whole `<section>` is behind `focused &&`). Every row and the focused card call the same `onGroom` handoff Board/Sessions use; the "Review" button on a `needs-review` focused card is visual emphasis only, same target. Overflow renders one "View all N → Sessions" link that just `setView('Sessions')`. No listeners added: #43's `state` event already triggers App's `refresh()`, and HomeView is a pure projection of `data.items` — confirmed in App.tsx's `chat:event` handler.
- **#43**: work-unit preamble joins the other prompts in prompts.ts, methodology-aware only if trivially so (charters vary; the assumptions contract does not). The Proposal fence schema is UNCHANGED — assumptions ride as a required section in the spec text, not a schema change, so `applyProposal` and `ProposalPreview` keep working; ProposalPreview may render the section distinctly if cheap.
  - *Decisions taken during implementation:* the session manager is `src/main/sessions.ts` — `handoff(repo, id, { run, emit })`, `WORK_UNIT_CAP = 3`, a module-level `active` set + FIFO `queue`, and `resetSessions()` as the test hook. It is deliberately NOT the drain loop: a work unit is one Turn with no retries, review cycle or worktree. Refusals: that session's own chat turn in flight, and a session already working/queued — and, since the review, main re-checks at *dequeue* time too (`claimable`: chat turn idle and the item still working/queued), because a queued session the user reclaimed by typing must never spawn a second Turn. `sendChat` calls the new `cancelQueued(repo, id)` where it clears `groomState`, and the one-Turn-per-session guard moved from `sendChat` into the shared `runTurn` so a work unit obeys it too. `transition()` stamps `lastActivity`, which is what makes the Sessions Queued group readable FIFO (it is ordered oldest-first there; every other group stays newest-first). `chat.ts` gained `chatBusy(slug)` for the first and `workUnitTurn()` for the Turn itself — `sendChat`'s body was extracted into a private `runTurn(..., workUnit)` so the two paths share the transcript/session/streaming plumbing. A work unit does *not* clear `groomState` (it runs because the session is `working`), suppresses the auto-title, always parks `needs-review` (proposal or not — the user must look either way), and writes a `Background draft failed (exit N).` assistant line when the Turn produced nothing. The prompt is `WORK_UNIT_PROMPT` in prompts.ts, methodology-agnostic, sent with `--resume` on top of the transcript (plus the groom preamble only if the session has no sessionId yet). Transitions push on the existing `chat:event` channel as a new `{kind:'state', state}` variant (no new channel; App just calls `refresh()`, since Sessions/Home are projections), and the `done` event gained `workUnit?: boolean` so the App toast says "finished its background draft". Dismiss now clears `needs-review` through the existing `session:reopen` IPC (slice 3's wart — same clear, no new handler); the only new IPC is `session:handoff`. GroomView takes a `groomState` prop, folds working/queued into its existing `sending` flag (composer, Send, Propose Now, mic, Handoff all disabled) and renders one state line above the composer. Assumptions are not rendered specially — they are Markdown inside the Spec and ProposalPreview shows the Spec.

- **#44**: interrupted/resume is quit-path only, and the notifier is injected — no Electron in Vitest.
  - *Decisions taken during implementation:* `sessions.ts` gained `interruptSessions()` (its `active` set became a `Map<string, Job>` so the in-flight jobs' repo/id survive to the quit path); `before-quit` calls it *before* `killTask()`/`killChats()`, so every working/queued session is `interrupted` on disk before its Turn is aborted. Resume is not new machinery: `session:resume` is a second `ipcMain.handle` on the same `startWorkUnit` helper `session:handoff` now uses, so a resume is a re-handoff — `workUnitTurn` already resumes the CLI session (`--resume`), which the research note confirms survives SIGTERM/SIGKILL with the same id. No orphan scan and no mid-turn crash recovery: a hard crash leaves the session `working`, and the user re-hands-off. Notifications: `chat.ts` (the only needs-review transition site) gained `setNotifier({ notify, isFocused })` — a module-level injected seam, null in tests by default; `index.ts` is the only file that touches `Notification`/`BrowserWindow`, checks `Notification.isSupported()`, and on `click` restores/focuses the window and pushes a new `session:open` channel (App navigates to that Groom). Unsigned dev builds show nothing — documented in the wiring comment, not fought. `interrupted` split out of the "Needs your review" group into its own Sessions group with a Resume row button (slice 3's parking undone), and GroomView renders an interrupted state line with the same Resume.
